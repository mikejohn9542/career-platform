## 1. Architecture decision

I chose an EC2 `t3.micro` running the app with a **Single-AZ RDS PostgreSQL** `db.t3.micro` in
us-east-1, rejecting both EC2 with PostgreSQL installed on the instance (~$13/month, but the app and
database would share one failure domain and backups would be manual) and Lambda with API Gateway
(which `next start` cannot run without an adapter, and which the IAM policy attached to my user
cannot provision anyway), accepting in exchange a second billable service at roughly $28/month
instead of $13 and one more resource to provision — because my priority was the option that is least
to operate, and managed backups and patching are what I was buying.

A finding worth recording: the live database holds a published project and a skill item that exist
**nowhere in the repository**. `npm run db:seed` deletes and rebuilds every table from
`src/content/profile.ts`, so running it against the real database would silently destroy published
content. It is now blocked by a guard in code that refuses to seed a database already holding
projects, verified firing against the real RDS data — not just a comment warning.

## 4. Cutover status

**My domain moved to AWS on 2026-11-09.** Status: **complete and verified.**

The cutover was not the planned, unhurried step. The Railway trial ended around 2026-11-07 while the
apex still pointed there, so `https://michaeljportfolio.me` was already serving Railway's
"application not found" `404` before I started this session. The guide's instruction to keep Railway
serving until the checks pass could not apply — the checks had passed on 2026-11-05, and Railway was
already gone. Cutover stopped being a decision and became the repair.

| Item | Before | After |
|---|---|---|
| Apex record | `CNAME` → the Railway service host | **`A` → the EC2 Elastic IP** |
| Proxy status | DNS only | DNS only (unchanged — this is what keeps HTTP-01 renewal working) |
| What the apex served | `404`, 101 bytes | `200`, 55,209 bytes |

**Screenshot of the DNS record:** [`ex07-dns.png`](ex07-dns.png) — it shows all three web records in
the zone: the apex and the `aws.` test subdomain both as `A` records pointing at the same Elastic IP
and set to **DNS only**, and `www` as the proxied placeholder that the redirect rule acts on.

The change was made as a single update request, so the record was never absent, with the previous
value saved to a file first in case it had to go back. `www` needed no change: it is a proxied
placeholder record with a Cloudflare redirect rule that bounces it to the apex, so it never reaches
the server — which is also why the certificate did not need a `www` name.

Verification after the cutover, from my laptop:

| Check | Result |
|---|---|
| `http://michaeljportfolio.me/` | `308` → `https://michaeljportfolio.me/` |
| `https://michaeljportfolio.me/` | `200`, 55,209 bytes — identical to the test subdomain |

| Content | All three projects present; `/privacy` and the resume PDF unchanged |
| Renewal | `certbot renew --dry-run` passed for both certificates; `certbot.timer` active |
| Reboot after cutover | Boot id genuinely changed, both services back `active`, site `200` from the internet in about 20 seconds |

**One security fix shipped with the cutover.** The app had been running as `ubuntu`, which is in the
sudo group, so a code-execution bug in the website would have meant root on the whole machine — my
own notes called this a blocker before cutover. It now runs as `careerplat`: a system account with no
login shell, in no group but its own, not in sudo, with read-only access to the code it runs and
write access to exactly one cache directory. While applying it I found that handing that account
group ownership while the build directories were still group-writable would have let the app rewrite
its own `node_modules` — which it executes — so group write was removed across the tree. Verified
live: the process runs as `careerplat`, `sudo` is refused for it, it cannot write `node_modules` or
`.next`, the deploy script still completes end to end, and the site survives a reboot.

**Still open, honestly:** Let's Encrypt has no contact email for this account, so if automated
renewal ever breaks, nothing will warn me — renewal is automated and dry-run tested, so this is a
missing backstop rather than a live fault. The old subdomain-only certificate also still exists and
still renews, harmlessly but pointlessly. And the Railway SSH key registered on 2026-11-03 to open
the backup tunnel is still on my Railway account and should be revoked.

## 5. Cost

**Estimate from section 6** (us-east-1, monthly). The EC2 line was verified against live pricing
data; the rest came from the public pricing feed or from memory, because the AWS Pricing API is not
in the policy attached to my IAM user and the AWS MCP server would not connect:

| Component | Monthly |
|---|---|
| EC2 `t3.micro` | $7.59 (verified live: $0.0104/hr × 730) |
| EBS gp3, 20 GB | ~$1.60 |
| Public IPv4 (Elastic IP, in use) | ~$3.65 |
| RDS `db.t3.micro` PostgreSQL, Single-AZ | ~$13.14 |
| RDS gp3 storage, 20 GB | ~$2.30 |
| Automated backups | $0 — free up to provisioned storage; the database is 8.6 MB |
| Data transfer out | $0 — under the 100 GB/month free allowance |
| **Estimated total** | **~$28/month** (the guide predicts ~$26) |

At ~$28/month, $100 of credits is roughly three and a half months. A public IPv4 address bills while
attached **and** while idle, so the Elastic IP must be released, not merely detached, if the instance
is ever stopped to save money.
