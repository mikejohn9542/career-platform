# Exercise 05: Investigate a DNS or TLS failure

## 1. Setting and prediction

**Setting:** This is the supplied simulation from the Exercise 05 handout, not my real system. The hostnames, IP addresses, and outputs are invented for the lab.

**Failed check:**

```
dig site.lab.example A +noall +answer
curl -Iv https://site.lab.example/
```

**Prediction:** Because the site was migrated onto railway, dig should show site.lab.example as a CNAME pointing to current-app.up.railway.app to match the new railway deployment's routing target, resolving to the current address. It should not return the old Azure address 198.51.100.24. curl should connect via port 443 on the railway address and receive a certificate whose name matches site.lab.example. If the verification is successful, it should show an HTTP status of 200.

## 2. Failed check and evidence

**Date:** Simulated output supplied in the Exercise 05 handout; reviewed 10/12/2026, not run by me.

**Actual result (simulated):**

```
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  A  198.51.100.24

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (198.51.100.24) port 443
* Server certificate: subject: CN=old-vm.lab.example
* SSL: certificate subject name does not match target host name 'site.lab.example'
curl: (60) SSL certificate problem: certificate subject name does not match target host name
```

**Compared with my prediction:** My prediction was that dig would show the new railway deployment routing target and that curl would receive a certificate that matches the new site. Instead, dig returned the wrong record type and address (an A record type instead of a CNAME meaning that it pointed to an IPv4 address instead of another domain name) and curl received a certificate from the old site that caused verification to fail.

## 3. Diagnosis

**Tracing DNS to TLS:** The name resolved to the site's old address on the Azure VM. Curl ended up connecting to that site as well, because site.lab.example still resolves to 198.51.100.24 and we used that in the curl command. When we connected to the server, it presented a certificate for the old site which has a different subject name causing the verification to fail. For it to be successful the subject names have to match meaning that the certificate would have to match the host name (site.lab.example) instead of old-vm.lab.example. The request never reached the intended site because the domain we gave the commands doesn't point to the new site yet.

**Which fault came first:** The DNS error occurs first because the domain we gave the command has a stale A record that points it in the wrong direction which is followed by the TLS error when the client tries to connect and receives a certificate that doesn't match the one it is checking for.

**What remains uncertain:** It is still uncertain whether we will still get a TLS error when we get to the new site because we don't know that the certificate is valid.

**Proposed repair:** My proposed fix would be to delete the A record and add a CNAME pointing to the railway address instead so that we get to the right place when entering the domain.

**Supporting evidence:** The dig command on the failed output gave me this result: `site.lab.example.  300  IN  A  198.51.100.24`. It shows an A record that points to the IP of the old site. Simply adding a CNAME that points to the new site (current-app.up.railway.app) should fix it.

## 4. Repair and repeated check

**Proposed change:** My proposed change was to delete the A record and add a CNAME pointing to the new railway address.

**Repeated check (simulated):**

```
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  CNAME  current-app.up.railway.app.
current-app.up.railway.app.  300  IN  A  203.0.113.44

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (203.0.113.44) port 443
* Server certificate: subject: CN=site.lab.example
* SSL certificate verify ok.
< HTTP/2 200
```

**Interpretation:** The output shows that my change was the right move and was what the operator who ran these commands did. The dig command shows `site.lab.example.  300  IN  CNAME  current-app.up.railway.app`, showing that the queried domain resolves to the right place. It also shows the record type as a CNAME instead of an A record, and the old address 198.51.100.24 no longer appears, so the A record was replaced rather than having a CNAME added next to it. The curl output shows a successful verification now because the certificate names match and the HTTP result is a 200.

**Compared with my initial proposal:** This supports my initial diagnosis: changing only the DNS record also fixed the TLS error, which confirms the TLS failure was caused by the stale A record and was not a separate certificate problem. I interpreted this output rather than running it.

## 5. What you learned

**A check that separates DNS from TLS:** A check that can separate a DNS problem from a TLS problem is by skipping DNS entirely by using curl --resolve:

```
curl -Iv --resolve site.lab.example:443:203.0.113.44 https://site.lab.example/
```

Using this command will send the request straight to the new railway address while still using the domain site.lab.example. If the regular curl fails but this one succeeds (certificate verifies and HTTP 200), it is a DNS issue because the name is pointing to the wrong place. If the new curl command fails, it is undoubtedly a TLS issue.

**If the failure remained:** If the failure remained after the CNAME change, I would first make sure I wait the full 300 second TTL before I try again. Then I would use a dig command to see if it is still pointing at the old A record. I would also check Railway to double check the custom domain and make sure I added the CNAME correctly.
